# 分支、CI 与测试环境部署

适用对象：维护 AlgoWiki 分支、测试环境和正式环境的开发者。

## 1. 分支职责与唯一晋级路径

| 分支 | 职责 | 允许的合并来源 | 部署行为 |
| --- | --- | --- | --- |
| `develop` | 日常开发集成 | feature / fix / security 分支 | 只运行 CI |
| `test` | 可部署的验收版本 | 仅 `develop` | CI 通过后自动部署到 `test.algowiki.cn` |
| `main` | 正式发布记录 | 仅 `test` | CI 通过后等待 production 人工审批 |

不要直接向三个长期分支推送，也不要把 `develop` 绕过 `test` 合并到 `main`。标准流程是：

1. 功能分支提交 Pull Request 到 `develop`。
2. `develop` 稳定后，创建 `develop -> test` Pull Request。
3. 测试站点自动部署完成后，按验收清单验证。
4. 验收通过后，创建 `test -> main` Pull Request。
5. `main` 流水线完成校验后，由发布负责人在 GitHub `production` Environment 中人工批准部署。

仓库的 `Promotion policy` 检查会拒绝不符合上述来源关系的 Pull Request。分支 ruleset 还应要求 Pull Request、必需状态检查、禁止 force push 和禁止删除。

## 2. CI/CD 流程

`.github/workflows/ci-delivery.yml` 对 Pull Request 和长期分支执行：

- Django 配置、迁移漂移和完整后端测试；
- 前端测试和生产构建；
- Compose 模型、Shell 语法和容器构建验证；
- 所有第三方 Action 使用完整 commit SHA 固定版本。

`test` 更新时，流水线只在上述检查成功后构建镜像。镜像同时带有完整 commit 标签和 OCI revision 标签；`test` Environment deployment 会把本次构建输出的精确 `sha256` 摘要写入授权 URL。服务器只读取同一 commit 的成功 GitHub Actions deployment 中携带的摘要并按 `@sha256:...` 拉取，不会从 `test`、`sha-<commit>` 或 `latest` 等可移动标签重新解析镜像。

`main` 更新时不会重新构建另一份生产镜像。流水线从已合并 Pull Request 的不可变元数据中取得当时的 `test` commit，并验证 `main` 源码树与它相同。生产服务器再从 root-only 的成功验收记录中读取该 commit 实际部署过的镜像摘要；不会重新解析可移动镜像标签，也不受后续 `test` 更新影响。

## 3. GitHub Environments 与服务器拉取

创建 `test` 和 `production` 两个 GitHub Environments。`production` 必须配置 Required reviewers；测试环境不设人工审批，以便 `develop -> test` 合并后自动部署。

GitHub-hosted runner 负责测试、构建、发布不可变镜像和写入 Environment 审批结果，不入站连接服务器。服务器上的 root-owned systemd timer 只通过 `api.github.com:443` 读取官方 `ci-delivery.yml` 的成功 `push` run，并主动从 GHCR 拉取镜像。

拉取器要求 run 对应当前 `test` 或 `main` 分支头。test 必须存在由 GitHub Actions 为同一 SHA 和同一 workflow run 创建且最终成功的 `test` Environment deployment，并从其受约束的授权 URL 取得构建输出摘要；production 除了完整成功的 main workflow，还必须存在同类 `production` Environment deployment，才会调用生产包装器。这样既不需要向 GitHub 公网 IP 开放 SSH，也不会把公开仓库的 PR 代码带到持久 self-hosted runner 上执行。

## 4. 首次安装受限部署通道

在维护者电脑生成单独的 Ed25519 密钥，不要覆盖已有密钥：

```powershell
ssh-keygen -t ed25519 -a 64 -f "$HOME\.ssh\algowiki_ci_test_ed25519" -C "algowiki-github-actions-test"
ssh-keygen -t ed25519 -a 64 -f "$HOME\.ssh\algowiki_ci_production_ed25519" -C "algowiki-github-actions-production"
```

将公钥和仓库中的三个文件安全上传到服务器临时目录，再以 root 执行：

```bash
cd /path/to/uploaded/deploy
./server-install-ci-deploy.sh \
  --test-public-key-file /path/to/algowiki_ci_test_ed25519.pub \
  --production-public-key-file /path/to/algowiki_ci_production_ed25519.pub
```

安装器会创建或收紧 `algowiki-deploy-test` 与 `algowiki-deploy-production`、安装 root 拥有的部署与备份命令、创建按环境隔离的最小 sudo 规则，并确保真实环境文件保持 `root:root 0600`。

再把 `server-poll-github-releases.py` 与 `server-install-release-poller.sh` 上传到服务器的同一临时目录，以 root 执行：

```bash
./server-install-release-poller.sh
```

安装器会写入 root-owned 拉取器、记录首次启用时间并创建三分钟周期的 systemd timer。首次启用时间以前的历史 workflow 不会被自动部署；重复安装会保留该安全边界。仓库为公开仓库，因此读取 GitHub API 不需要长期 Token，也不会在服务器保存 GitHub 凭据。

## 5. 环境隔离

| 项目 | 测试 | 生产 |
| --- | --- | --- |
| Compose project | `algowiki_test` | `algowiki` |
| 环境文件 | `deploy/.env.test` | `deploy/.env.production` |
| 本机端口 | `8002` | `8001` |
| Redis DB | `1` | `0` |
| 数据库 | 独立测试库 | 生产库 |
| 媒体数据 | 独立 volume | 生产 volume |

Compose 为 Web、审核 worker 和 Redis 设置独立的 CPU、内存、PID 和日志大小上限。测试环境默认配额更低，可在各自环境文件中覆盖。

## 6. 自动部署做什么

受限部署命令按顺序执行：

1. 校验环境名、完整 commit 和 GHCR 镜像摘要；
2. 拉取镜像并验证 OCI revision 与待部署源码 commit 一致；
3. 校验 Compose，启动并等待该环境的 Redis；
4. production 在迁移前创建数据库备份；
5. 在新镜像的一次性容器中运行 `check --deploy` 和迁移；
6. 切换 Web 与 worker，并等待容器健康；
7. 验证本机和公网 `/api/health/`；
8. 成功后才把镜像摘要和 release 写入环境状态。

测试环境还会按源码 commit 写入不可覆盖的成功摘要记录。相同 commit 后续若构建出不同摘要，自动部署会拒绝替换原验收记录并回滚；生产只接受这份记录中的摘要。

服务切换失败会尝试恢复上一个镜像。数据库迁移不会被自动反向执行，因此破坏性 schema 变更必须采用向后兼容的 expand/contract 方案。

## 7. 测试验收清单

- `https://test.algowiki.cn/api/health/` 正常；
- 首页、登录、个人中心、Wiki、动态、审核台和管理后台正常；
- 图片上传、审核、验证码与注册/找回流程正常；
- 数据库迁移无异常，Web 和 worker 日志无持续错误；
- 当前 release、镜像摘要和 `test` commit 能相互对应。
