# 午夜脉冲正式功能设计规格

## 1. 目标与边界

午夜脉冲把 AlgoWiki 的每日社区参与、Codeforces 训练和可积累反馈组合成一个稳定的日常入口。它必须做到：

- 北京时间每天 00:00 产生唯一的一期内容。
- 每期包含每日问答、每日挑战、争议投票三条信号。
- 每日挑战必须以 Codeforces 公开数据为证据，不能由前端自行标记完成。
- 积分、道具、签到、兑换和管理员操作必须可追溯、可防重放。
- 复用现有用户、问答、通知、权限和审计体系，不复制第二套社区模型。
- 正式实现继续位于 `codex/midnight-pulse-demo` 隔离分支，不部署到正式环境。

当前 `/pulse-demo` 的日蚀观测台视觉和临时暗夜主题已经通过验收。正式功能在此基础上接入真实 API，不另做一套普通表单风格。

## 2. 架构选择

采用独立 Pulse 业务域，并复用现有 `Question`、`Answer`、`UserNotification` 和 `SecurityAuditLog`。

不采用以下方案：

- 把每日状态和钱包写进 `User` 的 JSON 字段。该方案难以保证并发、唯一奖励和审计完整性。
- 依赖常驻任务队列在 00:00 创建内容。项目当前没有任务队列基础设施，定时器失败会导致当天不可用。

正式设计使用北京时间日期键和数据库唯一约束。当天首次请求在事务中原子创建每日一期，管理命令可以提前预热，但正确性不依赖外部定时器。

## 3. 每日生命周期

### 3.1 日期与截止时间

- 业务时区固定为 `Asia/Shanghai`。
- 每日一期的键为北京时间自然日，例如 `2026-07-19`。
- 新一期在当天 00:00 生效。
- 当日挑战的最终完成时间为次日 04:00。
- 00:00 至 04:00 期间，新一期和上一期未截止挑战可以同时存在。
- 问答首次奖励和投票只计入所属自然日，不延长到次日 04:00。

### 3.2 每日一期生成

每日一期记录以下稳定内容：

- 日期。
- 每日问答关联的 `Question`。
- 问题来源：管理员置顶、站内热点改写或题库随机。
- 争议投票题目及 2 至 5 个选项。
- 发布状态和创建来源。

生成优先级：管理员预设大于站内热点大于随机题库。生成后不因后续热点变化而替换，管理员只能通过有审计记录的编辑操作修改。

## 4. 社区问答与投票

### 4.1 每日问答

- 每日话题使用现有 `Question`，回答使用现有 `Answer`。
- 每日问题长期保持可阅读、可回答，不使用普通问答默认的七天自动关闭。
- 回答继续经过现有内容审核、封禁和通知逻辑。
- 用户当天第一条通过校验并可见的有效回答，点亮社区信号并获得 1 张换签卷。
- 每个用户每天最多获得一次回答奖励。
- 回答被隐藏或删除后不倒扣已获得道具，但管理员可以通过独立流水纠正滥用奖励。

### 4.2 争议投票

- 用户每期只能选择一次。
- 投票提交后不可修改。
- 提交成功后返回各选项票数、比例和总票数。
- 投票不直接增加积分，完成后点亮观点信号。

## 5. Codeforces 绑定与解绑

### 5.1 绑定验证

固定验证题为 `Codeforces 4A Watermelon`。该题只用于证明 Handle 归属，不是每日挑战题。

绑定流程：

1. 登录用户提交 Handle。
2. 服务端调用官方 `user.info` 确认 Handle 存在，并获取当前 Rating。
3. 服务端调用官方 `user.status` 记录最新提交 ID 作为基线。
4. 服务端创建 10 分钟有效的验证会话。
5. 用户在 Codeforces 重新提交并 AC `4A`。
6. 用户点击验证，服务端查找满足全部条件的新提交：
   - 提交 ID 大于基线。
   - `contestId=4` 且题目索引为 `A`。
   - `verdict=OK`。
   - 提交者 Handle 与待绑定 Handle 一致。
   - 提交时间位于验证会话有效期内。
7. 验证提交 ID 被永久标记为已使用，不能再次证明其他绑定。

同一用户同时只能拥有一个活跃绑定，同一 Handle 同时只能绑定一个用户。Handle 以大小写不敏感的规范值做唯一判断，同时保留 Codeforces 返回的展示大小写。

### 5.2 用户自助解绑

- 用户输入当前 AlgoWiki 密码确认。
- 解绑只结束活跃关系，不删除绑定历史、挑战证据、积分或签到。
- 解绑后的 Handle 在 7 天内只能由原用户重新绑定。
- 页面展示解绑时间、冷却结束时间和重新绑定资格。
- 自助解绑写入安全审计日志并发送站内通知。

### 5.3 管理员代为解绑

- 管理员可按 AlgoWiki 用户或 Codeforces Handle 搜索绑定关系。
- 解绑原因必填。
- 默认应用相同的 7 天转移冷却期。
- 管理员可为纠错或账号迁移明确选择立即允许重新绑定。
- 操作记录管理员、目标用户、Handle、原因、IP、时间和是否解除冷却。
- 目标用户收到站内通知。

## 6. 每日挑战

用户首次选择模式后，当天模式锁定。每天最多换签两次，每次消耗 1 张换签卷，只能在已锁定模式中抽取新目标，并排除当天已经出现过的目标。

### 6.1 模式 A

- 使用绑定账号当前 Rating。未定级账号按 800 处理。
- 目标难度为 `Rating + 300`，按 100 分档并限制在 800 至 3500。
- 从账号从未 AC 的题目中随机选择。
- 如果目标分档没有可用题，按距离由近到远搜索相邻 100 分档，并在界面标记实际难度。
- 分配时保存 Rating 快照、目标难度、题目标识和分配时间。
- 完成条件是分配后出现该题新的 `OK` 提交。
- 完成后增加 1 积分并记为当天签到。

### 6.2 模式 B

竞赛池按分配时 Rating 决定：

- Rating 小于 1400：Div.3 或 Div.4。
- Rating 1400 至 1899：Div.2。
- Rating 大于等于 1900：Div.1。

候选竞赛必须已经结束，不能是 Gym 或团队赛，且绑定账号对该场所有题目都没有历史提交。分配后保存竞赛题目快照和题目总数 `n`。

完成条件：

- 在分配后以 Codeforces `VIRTUAL` 身份产生提交。
- 在次日 04:00 前对该场至少 `n-2` 个不同题目获得 `OK`。
- 同一道题的多次提交只计一次。

完成后增加 3 积分并记为当天签到。

### 6.3 Codeforces 同步

- 只访问官方固定 API，不接受用户提供任意 URL。
- 服务端全局限制为至少 2 秒一次请求，并缓存 `user.info`、题库、竞赛列表和用户提交摘要。
- 绑定验证和完成检测由用户主动触发，不在前端高频轮询。
- API 超时或限流时保持原状态，不错误标记完成，并返回可重试提示。
- 每个完成证据提交 ID 只能结算一次。

## 7. 积分、道具和补签

### 7.1 不可变流水

积分和道具余额都由不可变流水汇总。每条流水包含：

- 用户。
- 资产类型。
- 变化量。
- 来源类型和来源 ID。
- 唯一事件键。
- 操作者和备注。
- 创建时间。

数据库对唯一事件键加唯一约束，重复请求不会重复发放。

### 7.2 换签卷

- 当天首次有效回答奖励 1 张。
- 管理员、活动和兑换码也可发放。
- 每日挑战最多消耗两张。
- 不能切换挑战模式。

### 7.3 补签卷

- 用户选择一个未签到的历史日期。
- 消耗后获得一个符合模式 A 规则的补签题。
- 该题必须在补签分配后 AC。
- 完成后目标日期记为已签到，并增加 1 积分。
- 补签不补发该日期的问答奖励或投票信号。

### 7.4 超级补签卷

- 用户选择一个未签到的历史日期。
- 消耗后立即标记该日期签到并增加 1 积分。
- 不需要 Codeforces 提交。
- 同一天不能被重复补签。

## 8. 连续签到与排行榜

- 普通每日挑战、补签和超级补签都可以产生签到日期。
- 当前连续天数从最近一个应签到日期向前计算。
- 最长连续天数保存为可重算快照。
- 每日问答、投票和挑战组成页面的 3/3 脉冲进度，但只有挑战完成决定签到。
- 排行榜支持总榜、当前连续榜、Rating 分段榜和学校榜。
- 总积分相同时，先完成者优先，再按用户 ID 稳定排序。
- 被封禁用户可以保留历史记录，但默认不进入公开排行榜。

## 9. 管理能力与兑换码

午夜脉冲管理区提供：

- 每日问题和投票预设、编辑、发布。
- Codeforces 绑定查询和管理员解绑。
- 单用户或批量发放三类道具。
- 活动奖励配置。
- 兑换码创建、禁用和使用记录查询。
- 积分及道具流水查询。

兑换码只在创建时展示一次明文，数据库保存安全摘要。兑换码支持开始时间、结束时间、总兑换次数、每用户次数、奖励负载和启用状态。兑换过程使用事务和行锁保证不会超发。

## 10. 数据模型

新增模型按职责拆分：

- `CodeforcesBinding`：活跃绑定、Rating 快照、同步状态和冷却信息。
- `CodeforcesVerification`：待验证 Handle、基线提交、有效期、状态和验证证据。
- `CodeforcesEvidence`：已使用提交 ID 和用途。
- `PulseDailyEdition`：每日问题、投票和发布日期。
- `PulsePollOption`、`PulsePollVote`：投票选项和不可重复投票。
- `PulseUserDay`：用户当日三条信号、模式锁定和签到摘要。
- `PulseChallengeAssignment`：模式、题目或比赛快照、换签序号、截止时间和完成证据。
- `PulseLedgerEntry`：积分和道具不可变流水。
- `PulseMakeup`：补签目标、类型、状态和关联挑战。
- `PulseRedemptionCode`、`PulseRedemption`：兑换规则和兑换记录。

数据库约束负责保证活跃 Handle 唯一、每日用户状态唯一、每日投票唯一、目标日期补签唯一、证据唯一和奖励事件唯一。

## 11. API 设计

用户接口：

- `GET /api/pulse/today/`：当前一期、个人状态、钱包和上一期未截止挑战。
- `POST /api/pulse/answers/`：发布每日回答并结算首次回答奖励。
- `POST /api/pulse/vote/`：提交不可修改投票。
- `POST /api/pulse/challenges/choose/`：锁定 A 或 B 并抽取目标。
- `POST /api/pulse/challenges/reroll/`：同模式换签。
- `POST /api/pulse/challenges/check/`：检查 Codeforces 完成证据。
- `POST /api/pulse/codeforces/bind/start/`：创建 10 分钟绑定验证。
- `POST /api/pulse/codeforces/bind/verify/`：校验新的 `4A` AC。
- `POST /api/pulse/codeforces/unbind/`：密码确认后自助解绑。
- `POST /api/pulse/makeups/`：创建普通或超级补签。
- `POST /api/pulse/redeem/`：兑换奖励码。
- `GET /api/pulse/atlas/`：签到日历和连续记录。
- `GET /api/pulse/rankings/`：排行榜。

管理员接口：

- `GET/POST/PATCH /api/pulse/admin/editions/`。
- `GET /api/pulse/admin/bindings/`。
- `POST /api/pulse/admin/bindings/{id}/unbind/`。
- `POST /api/pulse/admin/grants/`。
- `GET/POST/PATCH /api/pulse/admin/codes/`。
- `GET /api/pulse/admin/ledger/`。

所有写接口接受请求幂等键。未登录返回 401，被封禁用户返回 403，规则冲突返回 409，Codeforces 暂不可用返回 503。

## 12. 前端交互

- `/pulse-demo` 在正式接入后改为 `/pulse`，旧地址保留跳转，避免已保存链接失效。
- 未登录用户可浏览当日问题和投票摘要，但参与操作会打开登录提示。
- 挑战卡在未绑定时直接展示 Codeforces 绑定流程和验证倒计时。
- 个人中心增加绑定状态、自助解绑和冷却状态。
- 管理后台增加午夜脉冲分区，沿用现有管理页面组件结构。
- 页面进入时临时切换日蚀暗夜主题，离开后恢复用户原主题。
- 桌面视口保持单屏核心布局和隐藏页面滚动条，移动端按星体、问答、挑战、投票自然滚动。
- 状态切换使用短时弹簧缓动、淡入和形变，并尊重 `prefers-reduced-motion`。

## 13. 安全与审计

- Handle 只允许 Codeforces 合法字符并做长度限制。
- 不保存 Codeforces 密码、API Key、Cookie 或提交源码。
- 自助解绑必须校验当前密码。
- 管理员解绑、批量发券、兑换码操作和人工纠正都写入审计日志。
- 绑定、换签、结算、补签和兑换都在数据库事务中完成。
- 用户可见错误不暴露第三方原始响应、堆栈或内部限流状态。

## 14. 测试与验收

后端测试使用可注入的 Codeforces 客户端替身，测试期间不访问真实网络。至少覆盖：

- 绑定基线、10 分钟窗口、错误题目、旧提交、非 AC、证据重放和 Handle 唯一性。
- 用户自助解绑密码校验、七天冷却、原用户重绑。
- 管理员原因必填、默认冷却、冷却解除、通知和审计。
- 每日一期并发防重复。
- 问答奖励只发一次，投票不可修改。
- A 模式难度边界、未 AC 过滤、相邻分档回退、两次换签和完成结算。
- B 模式 Rating 分段、零历史提交、`VIRTUAL` 限制、`n-2` 和 04:00 截止。
- 积分及道具幂等、补签、超级补签、兑换码限额和排行榜并列。

前端测试覆盖 API 状态映射、绑定倒计时、模式锁定、换签余额、错误恢复和主题恢复。最终必须通过 Django 测试、前端测试、生产构建、迁移检查和桌面及移动浏览器验收。
